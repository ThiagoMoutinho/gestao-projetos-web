# REFATORAÇÃO VISUAL DO DASHBOARD — SHADCN/UI

## **1. CONTEXTO**

Estamos desenvolvendo o Sistema de Gestão de Projetos do IGEPPS, utilizando Next.js, React, TypeScript, Tailwind CSS e shadcn/ui.

A tela de login já foi aprovada e está funcionando com Better Auth.

O dashboard inicial foi implementado, porém não gostei da qualidade visual. A interface parece ter sido construída predominantemente com elementos HTML e estilização manual, sem aproveitar adequadamente os componentes e padrões do shadcn/ui.

Estou anexando a captura do dashboard atual.

## **2. OBJETIVO**

Refatorar visualmente o dashboard para obter uma interface moderna, elegante, consistente e profissional, aproveitando efetivamente os componentes oficiais do shadcn/ui.

Quero uma experiência semelhante à qualidade dos dashboards apresentados na documentação e nos exemplos oficiais do shadcn/ui.

Não quero apenas trocar cores ou arredondar bordas. Quero melhorar a composição, a hierarquia visual, o espaçamento, a tipografia e os componentes utilizados.

## **3. AUDITORIA OBRIGATÓRIA**

Antes de modificar qualquer arquivo:

1. Identifique os componentes shadcn/ui já instalados.
2. Identifique quais elementos do dashboard foram implementados manualmente.
3. Verifique a configuração do tema e dos tokens CSS.
4. Consulte os padrões e exemplos oficiais do shadcn/ui.
5. Apresente brevemente quais componentes existentes serão reutilizados e quais precisarão ser adicionados.

Não recrie manualmente componentes que já existem no shadcn/ui.

## **4. SIDEBAR**

Substituir a implementação manual, quando aplicável, pelos componentes oficiais:

- SidebarProvider
- Sidebar
- SidebarHeader
- SidebarContent
- SidebarGroup
- SidebarMenu
- SidebarMenuItem
- SidebarMenuButton
- SidebarFooter
- SidebarTrigger

Requisitos:

- Preservar o logotipo institucional do IGEPPS.
- Manter a identidade azul institucional.
- Melhorar a hierarquia dos itens de navegação.
- Destacar de maneira elegante a página ativa.
- Utilizar ícones Lucide consistentes.
- Adicionar separações visuais discretas quando necessário.
- Implementar corretamente o comportamento responsivo.
- Não habilitar páginas que ainda não foram implementadas.

## **5. HEADER**

Utilizar componentes shadcn/ui adequados para:

- Campo de busca.
- Avatar do usuário.
- DropdownMenu com informações da conta e ação de sair.
- Separadores e botões.
- Navegação responsiva.

Preservar os dados reais da sessão Better Auth.

Não implementar uma busca funcional sem endpoint disponível. Caso ainda não exista integração, apresentar claramente o estado indisponível, sem simular resultados.

## **6. INDICADORES**

Refatorar os cards de indicadores utilizando Card, CardHeader, CardContent e outros componentes oficiais adequados.

Indicadores previstos:

- Projetos em andamento.
- Projetos concluídos.
- Projetos em atraso.
- Projetos bloqueados.
- Aguardando documentação.

Melhorias desejadas:

- Tipografia mais refinada.
- Melhor hierarquia entre rótulo e valor.
- Ícones bem alinhados.
- Espaçamento consistente.
- Layout responsivo.
- Cores semânticas discretas.

Não inventar números, percentuais ou tendências.

Enquanto não houver integração, utilizar estados vazios claros e visualmente elegantes.

## **7. GRÁFICOS**

Preparar as seções:

- Projetos por área.
- Situação dos projetos.

Utilizar o padrão Chart do shadcn/ui com Recharts, caso essas dependências já estejam disponíveis ou sejam necessárias para a implementação futura.

Não gerar gráficos fictícios com números inventados.

Enquanto não houver dados, utilizar estados vazios bem apresentados.

## **8. PROJETOS EM ANDAMENTO**

Melhorar a seção de projetos utilizando:

- Tabs para alternar entre visualizações.
- Card para os elementos de projeto.
- Badge para situações.
- Button para ações.
- DropdownMenu para ações contextuais.
- Table para visualização em lista, quando implementada.

O Kanban deve apresentar colunas visualmente consistentes e preparadas para receber projetos reais.

Não implementar drag-and-drop nesta etapa.

Não criar ações ou navegações fictícias.

## **9. MARCOS, TAREFAS E COMUNICADOS**

Melhorar a composição dos painéis laterais.

Utilizar componentes shadcn/ui adequados, incluindo Card, Badge, Separator, Skeleton e estados vazios.

Evitar grandes caixas pontilhadas ocupando espaço sem necessidade.

Apresentar mensagens de ausência de dados de forma discreta e profissional.

## **10. PADRÃO DE FORMULÁRIOS**

Estabelecer como regra para os próximos módulos:

- Input do shadcn/ui para campos de texto.
- Checkbox do shadcn/ui, e não input HTML nativo estilizado manualmente.
- Select do shadcn/ui quando adequado.
- Dialog para janelas modais.
- AlertDialog para confirmações críticas.
- Form/Field com validação adequada.
- Button para ações.
- Label para identificação dos campos.
- Tooltip para informações complementares.

Componentes nativos podem existir internamente, mas não quero controles visuais improvisados quando houver um componente oficial apropriado.

## **11. DESIGN SYSTEM**

- Utilizar os tokens e variáveis do tema.
- Padronizar tipografia, espaçamento, bordas, sombras e estados interativos.
- Manter a identidade visual institucional do IGEPPS.
- Preservar acessibilidade e navegação por teclado.
- Implementar transições suaves e discretas.
- Evitar CSS duplicado e valores arbitrários desnecessários.
- Não copiar a aparência de um dashboard genérico sem considerar a finalidade institucional.

## **12. RESTRIÇÕES**

- NÃO modificar a tela de login aprovada.
- NÃO modificar o Better Auth.
- NÃO alterar backend ou banco de dados.
- NÃO criar dados fictícios.
- NÃO implementar novas regras de negócio.
- NÃO habilitar módulos indisponíveis.
- NÃO substituir componentes shadcn/ui por versões HTML feitas manualmente.
- NÃO reescrever o projeto inteiro.
- NÃO instalar bibliotecas redundantes.

## **13. VALIDAÇÃO**

1. Executar typecheck, lint e build.
2. Verificar o dashboard autenticado.
3. Testar a sidebar em desktop e mobile.
4. Testar dropdown de usuário e logout.
5. Verificar alinhamento e consistência visual.
6. Confirmar que não houve regressão na tela de login.
7. Informar quais componentes shadcn/ui foram efetivamente utilizados.

## **14. ENTREGA**

Apresentar:

- Resumo da auditoria inicial.
- Lista dos componentes shadcn/ui utilizados.
- Arquivos criados ou modificados.
- Resultado das validações.
- Captura de tela do dashboard atualizado.

Não iniciar a integração de dados reais ainda.

Aguardar minha aprovação visual antes de avançar para a próxima etapa.
