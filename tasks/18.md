# IMPLEMENTAÇÃO 03 — DETALHES DO PROJETO E SISTEMA DE TRANSIÇÕES SUAVES

## **1. OBJETIVO**

Estamos desenvolvendo o Sistema de Gestão de Projetos do IGEPPS para substituir completamente o OpenProject.

A listagem de projetos já está funcionando com dados provenientes da API.

Nesta etapa, quero:

1. Implementar a página de detalhes do projeto.
2. Implementar um padrão reutilizável de transições suaves entre páginas.
3. Melhorar a experiência de navegação entre Início, Projetos e Detalhes.
4. Preservar a identidade visual institucional já aprovada.

## **2. DIRETRIZ PERMANENTE DE INTERFACE**

ATENÇÃO: esta diretriz deverá ser respeitada em todas as próximas funcionalidades do sistema.

Toda navegação e interação visual deve utilizar transições suaves, consistentes, discretas e profissionais.

Não quero mudanças bruscas de tela, componentes aparecendo instantaneamente sem contexto visual ou mudanças repentinas de layout.

Essa exigência se aplica a:

- Navegação entre páginas.
- Troca de abas.
- Abertura e fechamento de menus.
- Modais e drawers.
- Expansão de seções.
- Cards interativos.
- Botões.
- Estados de carregamento.
- Atualização de conteúdos assíncronos.

As animações não podem prejudicar a performance, a acessibilidade ou a utilização do sistema.

## **3. ARQUITETURA DAS TRANSIÇÕES**

Inspecione primeiro a arquitetura atual do frontend Next.js.

Identifique:

- Estrutura de layouts.
- Componentes compartilhados.
- Sidebar.
- Sistema de navegação.
- Bibliotecas de animação já instaladas.
- Padrões existentes de loading e skeleton.
- Organização de rotas e componentes.

Implemente uma solução reutilizável para transições de página, evitando código de animação duplicado.

Priorize CSS e recursos existentes quando forem suficientes.

Não instale bibliotecas adicionais sem necessidade técnica justificada.

Não introduza soluções incompatíveis com o App Router, renderização do servidor ou hidratação do React.

## **4. TRANSIÇÕES ENTRE PÁGINAS**

Ao navegar entre Início, Projetos e Detalhes:

- Preservar a sidebar e o cabeçalho.
- Evitar flashes de conteúdo.
- Evitar desmontagem desnecessária de componentes compartilhados.
- Utilizar uma animação sutil de entrada do conteúdo.
- Preferir opacidade combinada com pequeno deslocamento vertical.
- Utilizar duração aproximada de 180 a 250 ms.
- Evitar animações exageradas.
- Manter a navegação responsiva.

Não bloquear a navegação aguardando o término de animações.

Não utilizar temporizadores artificiais para simular carregamento.

## **5. LOADING E FEEDBACK VISUAL**

Quando uma página depender de dados da API:

- Utilizar Skeleton do shadcn/ui.
- Preservar aproximadamente a estrutura do conteúdo.
- Evitar saltos de layout.
- Exibir estados de erro e vazio adequados.
- Evitar que o usuário veja conteúdo antigo como se fosse o novo.
- Não ocultar falhas de API com animações.

A transição deve funcionar tanto em navegação rápida quanto em conexões lentas.

## **6. ACESSIBILIDADE**

Respeitar prefers-reduced-motion.

Quando o usuário solicitar movimento reduzido:

- Desabilitar deslocamentos e animações não essenciais.
- Manter feedback visual apropriado.
- Preservar navegação por teclado.
- Manter foco e estados acessíveis.

Não utilizar animações que causem piscadas ou movimentos excessivos.

## **7. PÁGINA DE DETALHES DO PROJETO**

Ao clicar em um projeto da listagem, abrir a página correspondente.

Utilizar o identificador real do projeto na rota.

Não utilizar dados hardcoded.

Consumir os endpoints existentes da API.

A página deverá possuir inicialmente:

### **7.1 Cabeçalho**

- Nome do projeto.
- Situação operacional.
- Responsável principal.
- Gestor do projeto.
- Navegação de retorno para Projetos.
- Identificação do projeto e área, quando disponíveis.

### **7.2 Visão Geral**

Apresentar os dados disponíveis na API:

- Informações gerais.
- Descrição.
- Responsáveis.
- Situação.
- Datas existentes.
- Dados de acompanhamento disponíveis.

Não inventar indicadores, percentuais ou datas.

### **7.3 EAP**

Apresentar a estrutura existente:

- Fases.
- Tarefas.
- Marcos.
- Datas planejadas e vigentes.
- Status.
- Responsáveis disponíveis.
- Percentuais registrados, quando disponíveis.

A organização deverá facilitar a compreensão da hierarquia entre fases, tarefas e marcos.

Utilizar componentes do shadcn/ui adequados à estrutura.

### **7.4 Abas Futuras**

Preparar a navegação visual para:

- Pendências.
- Entregas e Homologações.
- Histórico Executivo.
- Documentação.

Não implementar funcionalidades sem endpoints existentes.

Se alguma seção ainda não estiver disponível, utilizar uma indicação clara e discreta de funcionalidade futura, sem simular dados.

## **8. COMPONENTES SHADCN/UI**

Preservar:

- Sidebar institucional azul.
- Cabeçalho existente.
- Tipografia.
- Espaçamentos.
- Paleta de cores.
- Padrão de tabelas.
- Padrão de badges.
- Responsividade.

Não redesenhar o sistema.

Não modificar o dashboard inicial além do necessário para corrigir a transição de navegação.
