# **PREPARAÇÃO DE DADOS FICTÍCIOS PARA VALIDAÇÃO VISUAL DO CRONOGRAMA**

Quero preparar o ambiente descartável `gp_preview_97` com dados fictícios para conseguir visualizar e validar integralmente a página do Cronograma.

A tela atualmente apresenta "Não foi possível consultar o cronograma do projeto". Suspeito que o projeto utilizado não tenha registros suficientes para demonstrar todos os componentes.

## **1. Primeiro: diagnóstico**

Antes de cadastrar dados:

- Verifique se o endpoint do Cronograma responde corretamente.
- Consulte os logs da API.
- Verifique se a resposta HTTP é 200, mesmo quando não existem registros.
- Diferencie ausência de dados de falha de consulta.
- Corrija eventuais problemas de integração ou consulta antes de inserir a massa de demonstração.

Não utilize dados fictícios para esconder erros da API.

## **2. Massa de dados fictícios**

Utilize exclusivamente o banco `gp_preview_97`.

Prepare dados coerentes para o projeto `demo-proj-05`, cobrindo:

- Fases e atividades.
- Datas planejadas.
- Linha de base.
- Prazo vigente.
- Datas reais de execução.
- Progresso das atividades.
- Marcos.
- Reprogramações aprovadas e rejeitadas.
- Solicitações pendentes de análise.

Crie pelo menos quatro fases com situações diferentes:

1. Concluída.
2. Em andamento.
3. Atrasada.
4. Ainda não iniciada.

Inclua marcos aprovados e pendentes, e pelo menos duas solicitações de reprogramação aguardando análise.

## **3. Coerência dos dados**

Os registros devem estar relacionados corretamente:

- Atividades vinculadas às fases.
- Marcos vinculados às fases ou atividades correspondentes.
- Reprogramações vinculadas aos objetos cujo prazo foi alterado.
- Linha de base preservada.
- Prazo vigente compatível com as reprogramações aprovadas.
- Datas reais coerentes com a execução.
- Progresso compatível com a situação apresentada.

Não crie registros soltos ou inconsistentes apenas para preencher os cards.

## **4. Segurança do ambiente**

- Não altere o banco principal.
- Não altere o banco de prévia oficial.
- Não execute migrations nesses bancos.
- Trabalhe exclusivamente no `gp_preview_97`.
- Crie um script de seed reproduzível e idempotente.
- Identifique claramente os registros de demonstração.
- Não apague dados preexistentes sem autorização.

## **5. Validação visual**

Depois de preparar os dados:

1. Abra `demo-proj-05?aba=cronograma`.
2. Confirme que os cinco indicadores carregam.
3. Confira as barras da linha de base, prazo vigente e execução.
4. Confira os marcos.
5. Confira o histórico de reprogramações.
6. Confira as solicitações pendentes.
7. Confira a tabela comparativa de datas.
8. Teste também a Visão Geral.
9. Verifique que não existem erros 4xx ou 5xx nas consultas.

Apresente capturas reais do navegador com os dados carregados.

## **6. Entrega**

Informe os dados criados, o script utilizado, os endpoints testados e os resultados da validação.

Não faça push, merge ou rebase.

O objetivo é termos um ambiente de demonstração consistente, que permita avaliar visualmente todas as funcionalidades sem modificar os bancos oficiais.
